# Prompt for DeepSeek

DeepSeek работает через копипаст (нет прямого доступа к репо). Этот промпт — стартовый контекст плюс шаблон для постановки задач.

---

## Стартовое сообщение для DeepSeek (в начале новой сессии)

```
Контекст: я работаю над B2B-порталом для Leather Parfum на Shopify Dawn.
Проект ведут несколько AI-агентов: ты (DS) — code review и дебаг,
Gemini (GM) — дизайн, Claude Code (CC) — правки в репо,
Claude в чате (CL) — координация и документация.

В репо есть папка /docs со всей документацией. Сейчас я скопирую тебе ключевые файлы:

[вставить содержимое /docs/REQUIREMENTS.md]
[вставить содержимое /docs/ARCHITECTURE.md]
[вставить содержимое /docs/DECISIONS.md]
[вставить содержимое /docs/PROGRESS.md]
[вставить содержимое /docs/BUGS.md]

После того как прочитаешь — скажи:
1. Какие архитектурные риски ты видишь
2. Какие баги в BUGS.md можно закрыть силами code review без доступа к live-shop
3. Какие 3 пункта в PROGRESS Pending являются самыми важными к закрытию

Не предлагай решений противоречащих ARCHITECTURE.md — это уже зафиксировано пользователем.
```

---

## Шаблон постановки задачи DeepSeek

Когда у DS появляется конкретная задача (review секции, дебаг бага):

```
Задача: <одно предложение>

Контекст из документации (что должен помнить):
- Архитектурное правило: <ссылка на пункт из ARCHITECTURE.md>
- Связанный баг (если есть): <ссылка на BUGS.md #N>
- Связанное решение: <ссылка на DECISIONS.md D-N>

Файл/код для review:
[вставить содержимое .liquid / .js]

Вопрос:
- <что конкретно проверить>

Формат ответа:
- Severity: Critical/High/Medium/Low
- Что не так (с ссылками на строки)
- Как фиксить (псевдокод или Liquid-сниппет)
- Что протестировать после фикса
```

## Чего НЕ делает DeepSeek в этом проекте

- ❌ Не правит файлы напрямую (он не в репо) — только даёт суждения, применяет CC или CL
- ❌ Не решает дизайн-вопросы — это к Gemini
- ❌ Не принимает архитектурные решения за пользователя — флагает в DECISIONS.md, CL спрашивает Машу

## Output формат от DeepSeek

DS пишет диагнозы. CL и CC должны их интерпретировать в правки. Если DS говорит «фикс таков:», CL/CC применяет.

При расхождении между мнением DS и архитектурой проекта — приоритет у архитектуры (ARCHITECTURE.md). DS может ошибаться от недостатка контекста.

## Известные сильные стороны DeepSeek в этом проекте

- Поиск broken event chains в JS (нашёл `cart:refresh` → `cart:updated` баг)
- Аудит wholesale gating
- Отлов dead code (нашёл `progress_raw` неиспользуемую переменную)
- Поиск edge cases (divide by zero на margin calc)

## Известные слабые стороны

- Нет доступа к live-shop — не видит DOM, рендеренный HTML, реальное поведение
- Нет доступа к админке Shopify — не видит метафилды, теги, app config
- Нет доступа к Massy app — не видит что эта app рендерит на наших страницах

Поэтому всё что требует «посмотреть на живой странице» — задача US или Claude Code (через MCP с браузером).
